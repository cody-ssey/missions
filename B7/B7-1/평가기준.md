# B7-1 평가기준

2026-10-07 사용자가 평가 화면 사진으로 제공했다. 항목 1의 앞부분 몇 줄은 사진에서 잘려 확인하지 못했다(README/기술 문서에 시스템 구조(간단 아키텍처, 주요 컴포넌트 역할)가 포함되어 있다 등).

## 1

- README/기술 문서에 시스템 구조(간단 아키텍처, 주요 컴포넌트 역할)가 포함되어 있다 (일부 잘림)
- README/기술 문서에 API 명세(요청/응답 예시 포함)가 포함되어 있다
- README/기술 문서에 DB 구조(테이블/필드 또는 ERD)가 포함되어 있다
- README/기술 문서에 DB 확인 방법이 안내되어 있다 (DB 파일 경로/확인 절차/스크립트/조회 API 중 1개 이상)
- README/기술 문서에 팀 역할 및 개인별 작업 요약이 포함되어 있다
- 회원가입 기능이 동작한다
- 로그인 기능이 동작한다
- 로그인/비로그인 상태에 따라 접근 가능한 기능이 구분된다(예: 비로그인은 챗 기능 불가)
- 웹 UI에서 질문 입력이 가능하고, 응답이 화면에 출력된다
- 질문 입력 -> 서버 처리 -> AI API 호출 -> 응답 출력 흐름이 끊김 없이 동작한다
- 사용자 질문/AI 응답이 DB에 저장된다(최소: 사용자/시간/질문/응답 추적 가능)
- 사용자 기준으로 대화 로그 조회/추적이 가능하다 (내 로그 화면/조회 API/관리자 조회/제공 스크립트 중 1개 이상)
- AI API 실패/타임아웃 상황에서 서비스가 비정상 종료되지 않는다
- 오류 발생 시 사용자에게 오류 안내(메시지/상태코드 등)가 제공된다
- 사용자 입력 검증(빈 입력/길이 제한 등) 로직이 최소 1개 이상 존재한다

## 2

- FastAPI 프로젝트 구조가 역할 단위로 구분되어 있다(예: router/api, service, model/schema 등)
- API 라우트가 목적에 맞게 분리되어 있다(예: auth, chat, logs 등)
- 요청/응답 스키마를 사용하거나, 입력/출력 형식을 일관되게 관리한다
- 인증 처리 로직이 코드 상에서 분리/재사용 가능하게 구성되어 있다(예: dependency, middleware 등)
- DB 접근 로직이 라우터에 과도하게 섞이지 않고 분리되어 있다(모듈/CRUD/리포지토리 등 형태 자유)
- 민감정보(API 키 등)가 코드에 하드코딩되어 있지 않다(환경 변수 기반)
- .env 예시 제공 및 .gitignore 적용으로 민감정보가 저장소에 노출되지 않는다
- PR 기반 머지 기록이 존재하고, 작업 브랜치 흐름이 확인된다

## 3

- REST 관점에서 API가 목적에 맞는 엔드포인트/메서드로 설계되어 있다(일관성/예측 가능성)
- 인증/인가가 "왜 필요한지"가 서비스 흐름에 반영되어 있다(비로그인 접근 제한 근거가 동작으로 확인)
- AI API 호출이 서버에서 수행되어 클라이언트에 키가 노출되지 않는다
- AI 호출 실패/지연을 고려한 정책이 코드/동작으로 확인된다(타임아웃, 예외 처리, 사용자 안내)
- 대화 로그를 왜 저장하는지(추적/운영/개선) 목적이 문서 또는 기능(로그 조회/확인 절차)으로 이어진다
- 로그에 "운영 추적에 필요한 사건(요청/AI/DB)"이 남아, 문제 발생 시 원인 추적이 가능하다
- 협업 산출물(문서의 역할/작업 요약)이 Git 이력(커밋/PR)과 크게 모순되지 않는다
